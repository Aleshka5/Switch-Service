# ТЗ: Switch-Service — control plane для инференса

> **Статус:** исправленная спецификация v2, ей соответствует код в этом репозитории.
> **Стек:** Python 3.11+, стандартная библиотека + PyYAML. Не Go.
> **Черновик v1** (слабая модель) оставлен только как список ошибок ниже. Реализация идёт по этому файлу.

Сервис переводит каждую модель по треугольнику `off` — `cpu` — `gpu`, перед стартом проверяет бюджет RAM и VRAM и помнит желаемое состояние. Его можно встроить в другой Python-процесс (`SwitchCore`) или поднять отдельным HTTP API и ходить в него из gateway, CI или скрипта. Админка, Jenkins и правки чужих репозиториев в этот репозиторий не входят.

## 2. Состояния

Три вершины. Ребро есть между каждой парой. Запрос текущей вершины — не ребро.

```
        off
       /   \
      /     \
    cpu ——— gpu
```

| Откуда | Куда можно |
|---|---|
| `off` | `cpu`, `gpu` |
| `cpu` | `off`, `gpu` |
| `gpu` | `off`, `cpu` |

Один запрос — один переход. `cpu → gpu` не заходит в `off` как в желаемое состояние. Внутри рантайм может остановить контейнер и создать другой (другие device, env, command). Для вызывающего это один переход `from=cpu, to=gpu`.

Повтор той же вершины:

- сервис уже `ready` и контейнер совпадает с каталогом — `202 {"noop": true}`, контейнер не трогается;
- контейнер разъехался с каталогом (`drift`) — тот же запрос пересоздаёт его;
- прошлая попытка упала — тот же запрос является повтором.

Фазы рантайма, они не входят в треугольник: `off`, `starting`, `ready`, `stopping`, `failed`.

Пока по сервису есть переход со `status=running`, новый `POST` даёт `423 BUSY`. `force` это не отменяет.

Профиль может отсутствовать или быть `available: false`. Ребро треугольника при этом есть: API отвечает `422 STATE_NOT_SUPPORTED` и отдаёт `reason`. Так у image нет CPU-профиля (offload всё равно требует GPU), а CPU у LLM выключен, пока не передан `force`.

`transitions_allowed` в снимке — две соседние вершины. Пока идёт переход, список пуст. `retry_state` — вершина, которую имеет смысл запросить ещё раз, если сервис не `ready`.

## 3. Что делает один переход

`POST /api/services/{id}/state` сначала проверяет (синхронно, без записи в под), потом резервирует и возвращает `202`. Долгий старт идёт в воркере. В тестах и при `synchronous=True` тот же код выполняется в вызывающем потоке.

1. Вершина из `{off, cpu, gpu}`, сервис есть в каталоге, профиль существует. Иначе `400` / `404` / `422`.
2. `options.references` — целое `0..max_references` (по умолчанию 10) и только у профиля с `vram_per_reference_mib`. Неизвестные поля тела — `400`. Пропущенные `options` не сбрасывают уже сохранённые.
3. Admission (§4). Не влезает — `409`, контейнеры не меняются. `evict` — разрешение остановить, не приказ. Останавливается кратчайший префикс, без которого новый клейм не проходит. Сервис с `preemptible: false` в этом префиксе требует `force`, иначе `409 CANNOT_EVICT`.
4. Резерв пишется сразу: на время перехода держится `max(старый, новый)` по RAM и по VRAM, чтобы окно замены не отдало память соседу. Для `off` старый резерв держится, пока контейнер не остановится.
5. Выселение, затем старт или останов. `off` останавливает контейнер и не удаляет его. Смена профиля удаляет контейнер, если `config_hash` (образ, command, env, devices, mounts, сети, лимит памяти) изменился.
6. Health: процесс жив и, если задан URL, отвечает 2xx до `startup_timeout_s`. Иначе `CONTAINER_EXITED` или `HEALTH_TIMEOUT`.
7. Успех: `state=ready`, `mode` = вершина, desired фиксируется, резерв становится точным клеймом, пишутся замеры.
8. Провал: одна попытка вернуть предыдущую вершину. Получилось — сервис снова на ней, переход `failed`. Не получилось — `state=failed`, `fail_sticky=true`, desired = прошлая вершина, резерв снимается. Reconciler sticky не трогает, пока не придёт новый запрос.

Выселение, которое уже остановило соседа, назад не откатывается: его desired становится `off`.

Падение процесса посередине не ставит sticky. `recover()` снова ставит незавершённый переход в очередь.

## 4. Память

Два независимых «влезает». Пускать можно только если проходят оба.

**Журнал клеймов** (источник истины для управляемых сервисов):

```
budget  = total - reserve
free    = budget - сумма резервов других ready/starting/stopping
нужно   = клейм нового профиля
```

Свой текущий резерв из суммы исключается: сервис заменяется, а не добавляется к себе. Выселяемые тоже исключаются из гипотезы, но их контейнеры ещё живы, пока воркер их не остановит. Следующий запрос видит их резерв, пока останов не записан.

**Живой замер** не вычитает клеймы ещё раз:

- RAM: `MemAvailable + RSS тех, кого мы остановим - новый клейм >= ram_reserve`. `MemAvailable` уже не содержит RSS запущенных моделей. Второй раз вычитать их клейм нельзя: рядом с image (клейм 32 GiB, свободно ~40 GiB) отказался бы даже OCR на 1 GiB.
- VRAM: вес сервиса = `max(замер, клейм)`. Неизвестное = `max(0, nvidia_used - сумма весов)`. После плана занято = неизвестное + веса тех, кто остаётся. Свободно = `(total - reserve) - занято`.

Замер — факт о запущенном контейнере, а не история сервиса. `measured_vram_mib` попадает в admission только пока сервис `ready` в режиме `gpu`, `measured_ram_mib` — пока он `ready` в любом режиме. Остановка (`off`, вытеснение) обнуляет оба замера и `measured_at`. Иначе число из прошлого прогона держит карту за выключенный сервис: LLM с замером 28076 MiB после `off` оставлял «84 MiB свободно» на почти пустой карте, и embedder на 1536 MiB не переключался в `gpu`.

Поэтому:

- image с клеймом 20 GiB и простоем 440 MiB не «освобождает» карту. LLM на 30720 MiB рядом не стартует.
- Тот же LLM после `evict: ["image"]` считается против полного бюджета, а не против 440 MiB.
- Чужой процесс, который раздул `nvidia-smi` выше суммы клеймов, виден как неизвестное и может дать `409`, даже если журнал ещё пускает.
- `force` ни одну из этих проверок не отключает.

Калибровка VRAM при успешном старте — дельта `nvidia-smi` до и после. Для `calibrate_vram: false` (ленивая image) дельта в простое занизила бы клейм, поэтому замер VRAM не пишется и в admission остаётся клейм каталога. Если замер RAM или VRAM больше клейма в 1.15 раза, в снимке `over_budget: true`.

В ответе:

- `budget_mib` = `total - reserve` (не `MemAvailable - reserve`);
- `claimed_mib` = сумма текущих резервов;
- `ledger_free_mib` = `budget - claimed` (на время замены может быть меньше нуля: держится `max(старый, новый)`);
- `live_free_mib` = сколько реально свободно с учётом чужих процессов (для RAM — `MemAvailable - reserve`);
- `free_mib` = `min(ledger_free_mib, live_free_mib)` и `free_source` — `ledger` или `live`. Это ровно то число, против которого admission будет считать новый клейм, поэтому шапка админки и ошибка `409` не расходятся. Раньше здесь был только журнал: «27.5 GiB free» в шапке при «84 MiB left» в отказе;
- `unmanaged_mib` (только VRAM) — занято, но ни одному управляемому сервису не принадлежит;
- `available_mib` у хоста — сырой `MemAvailable`, справочно.

Отказ `409` содержит `required_mib`, `available_mib`, `holders`, `suggestions[]` с `evict`, `frees_*_mib`, `requires_force`, `enough`.

## 5. HTTP

База `/api/services`. Тело и ошибки — JSON. Код ошибки стабильный, текст — для человека.

Без `SWITCH_TOKEN` сервис слушает как локальный (по умолчанию `127.0.0.1`). С токеном принимаются `Authorization: Bearer` и `X-Service-Token`, сравнение постоянное по времени. `/healthz` и `/readyz` токен не требуют. Актор: `X-Auth-Email`, иначе `service`, иначе `local`.

| Метод | Путь | Результат |
|---|---|---|
| `GET` | `/api/services` | снимок: хост, сервисы, `active_transitions` |
| `GET` | `/api/services/{id}` | один сервис |
| `POST` | `/api/services/{id}/state` | переход, `202` |
| `POST` | `/api/services/{id}/actions/restart` | пересоздать текущий cpu/gpu |
| `POST` | `/api/services/{id}/actions/recalibrate` | переснять RAM, без рестарта |
| `GET` | `/api/services/{id}/logs?tail=` | текст, секреты вырезаны, хвост до 2000 строк |
| `GET` | `/api/services/transitions?limit=` | история |
| `GET` | `/healthz` | процесс жив |
| `GET` | `/readyz` | сокет рантайма доступен |
| `GET` | `/metrics` | Prometheus |

Тело перехода:

```json
{"state": "gpu", "evict": ["image"], "force": false, "options": {"references": 2}}
```

`state` обязателен. Ответ `202`:

```json
{"noop": false, "transition": {"id": "t_…", "service_id": "image", "from": "off", "to": "gpu",
  "status": "running", "phase": "admission", "actor": "local", "evict": []}}
```

Фазы: `admission`, `evicting`, `creating`, `starting`, `warming`, `committing`.

| HTTP | `error.code` | Когда |
|---|---|---|
| 400 | `BAD_STATE`, `BAD_OPTIONS`, `BAD_CATALOG` | вершина, поле, ссылки, каталог |
| 401 | `UNAUTHORIZED` | нет токена, хотя он включён |
| 404 | `UNKNOWN_SERVICE`, `NOT_FOUND` | нет id или маршрута |
| 409 | `INSUFFICIENT_VRAM`, `INSUFFICIENT_RAM`, `CANNOT_EVICT`, `BAD_STATE` | не влезает, нельзя вытеснить, restart у `off` |
| 422 | `STATE_NOT_SUPPORTED` | нет профиля или `available: false` без `force` |
| 423 | `BUSY` | переход уже идёт |
| 502 | `CONTAINER_EXITED`, `HEALTH_TIMEOUT`, `RUNTIME_FAILED`, `IMAGE_MISSING` | рантайм не поднял контейнер |
| 503 | `RUNTIME_UNAVAILABLE` | нет сокета podman или нет сэмпла GPU, а клейм VRAM > 0 |

Форма ошибки: `{"error": {"code", "message", "details?"}}`.

В снимке сервиса нет `env` и `command`. Секреты из `${VAR}` маскируются в логах.

## 6. Каталог

`config/services.yaml` — демонстрация на фиктивном хосте (`sample: fixture`), чтобы `make run` работал без GPU.

`config/services.homelab.example.yaml` — пример четырёх моделей. `sample: live`. Секреты только через окружение или `SWITCH_SECRETS`.

Правила:

- Профиля `off` нет: это отсутствие контейнера.
- `command` заменяет команду контейнера. Для своих образов OCR/embedder его нет, режим — переменная окружения.
- Один образ может обслуживать оба режима: у OCR и embedder это CUDA-сборка (`:cuda`) с переменной `OCR_LLAMA_NGL` /
  `EMBEDDING_LLAMA_NGL` (`0` — CPU, `999`/`-1` — все слои на GPU). Каталог различает режимы только env и `devices`,
  пересборка при переключении не нужна.
- Устройство GPU — строка CDI в `devices`, не `deploy.resources`.
- `host.network` — одна именованная bridge-сеть на все сервисы. Создаётся самим сервисом (идемпотентно, до первого
  контейнера) через libpod API; `host.network_subnet` необязателен и только для фиксированной подсети.
- `ports` понимает три формы: `container`, `host:container`, `ip:host:container`. Третья — единственный способ отдать
  порт наружу и оставить его на loopback: `"127.0.0.1:18090:8090"`. Пробы живости в общем случае идут именно так,
  потому что из rootless-контейнера имя не резолвится на хосте, а IP контейнера с хоста недостижим
  (см. [models-network.md](models-network.md)).
- `memory_limit_mib` по умолчанию = клейм RAM + `memory_headroom_mib` (2048). Это cgroup, не клейм admission.
- `restart_policy` всегда `no`. Поднимает reconciler, не podman. Иначе `off` недостижим (`Restart=always` у quadlet image).
- Имена контейнеров задаёт каталог. Кто ещё делает `podman start` этих имён, ломает инвариант «писатель один».

Смена файла каталога сама контейнер не перезапускает. Снимок показывает `drift: true`. Чинит `POST` той же вершины или `actions/restart`.

## 7. Рантайм и загрузка

`SWITCH_RUNTIME=fake` (по умолчанию для `make run`) ничего не запускает. `podman` ходит в libpod API по unix-сокету (`CONTAINER_HOST` или `/run/user/$UID/podman/podman.sock`).

Перед первым контейнером создаётся `host.network`, если его нет: `GET /libpod/networks/{name}/json`, при `404` —
`POST /libpod/networks/create`. Ответ `409` значит, что сеть создал кто-то другой, и это тоже успех. Проверка одна на
процесс, поэтому сеть можно не создавать ни compose, ни скриптом.

Reconciler (`reconcile_interval_s`, по умолчанию 15 с):

- desired `off`, а контейнер запущен — останавливает;
- desired `cpu`/`gpu`, а контейнер не тот или мёртв — догоняет;
- `fail_sticky` — пропускает.

Желаемое состояние лежит в SQLite и переживает рестарт процесса. Контейнеры при падении процесса не убиваются.

Как это запускать руками и чем не должен заниматься Makefile — в [operations.md](operations.md).

## 8. Встраивание

```python
from switch_service import SwitchCore

core = SwitchCore.open("config/services.yaml", db_path="var/switch.sqlite", synchronous=True)
core.set_state("alpha", "gpu", actor="rag-chat")
core.snapshot()
```

HTTP включается отдельно (`switch-service serve` или `switch_service.api.serve`). Чужой сервис может оставить себе только `SwitchCore` и не поднимать порт.

Роли, gateway и SPA сюда не входят. Когда появится gateway, ему достаточно маршрута на этот API с уже существующей проверкой admin. Токен — для машины, не для браузера.

## 9. Приёмка

1. Из `off` сервис переходит в `cpu` и в `gpu`; из `cpu` — в `gpu` и в `off`; из `gpu` — в `cpu` и в `off`. В истории один переход на ребро, `from` не становится `off` по дороге из `cpu` в `gpu`.
2. Повтор здорового состояния — `noop`, без вызовов рантайма.
3. Два GPU-клейма, которые не помещаются в `total - reserve`, дают `409 INSUFFICIENT_VRAM` с цифрами и подсказкой. Контейнеры не меняются. Это верно и когда `nvidia-smi` показывает простой.
4. `evict` останавливает только нужный префикс. `preemptible: false` без `force` — `409 CANNOT_EVICT`. С `force` бюджет всё равно проверяется.
5. Нет профиля или `available: false` — `422`. С `force` профиль `available: false` стартует, только если влезает.
6. Падение старта возвращает предыдущую вершину. Если вернуть нельзя — `failed` + sticky, reconciler не зацикливается.
7. Запрос во время перехода — `423`.
8. Рестарт процесса доигрывает незавершённый переход. Сервис, который был `off`, не поднимается сам.
9. В снимке и в логах нет значений секретов.
10. `podman` payload: `restart_policy=no`, CDI в `devices[].path`, без `HostConfig.DeviceRequests`.
